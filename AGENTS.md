# kindle-drop

kindle-drop is an Android app built with Expo and React Native. It is ril's personal reading app, and it starts as a foundation: app variants, Effect state and persistence, theming, a UI kit, and navigation. Product features arrive later.

The architecture is adapted from [T3 Code](https://github.com/pingdotgg/t3code)'s mobile app. When you need a pattern this repo does not have yet, look at how T3 Code's `apps/mobile` solves it before inventing one, then port only what the feature needs.

## A note from ril

I like building complex things as simply as possible. Channel "yagni" and fight scope creep. Do not preserve complexity because it exists, and do not add machinery because it looks impressive. Understand the real constraint, then build the smallest model that makes the correct behavior unsurprising.

These instructions are good defaults, not hard rules. My direct requests override anything here. If a rule fights the task in front of you, say so before breaking it.

## The ways to hurt yourself

1. **Killing by pattern.** Never `pkill -f`, `pgrep | kill`, or kill a PID you found by matching a name or path. Your own agent process has this checkout's path in its argv. Kill only a PID you captured at spawn, or the owner of your port from `ss -H -ltnp` after confirming `/proc/<pid>/cwd` is this checkout.
2. **Touching the real install.** The production app (`com.listlessbird.kindledrop`) is ril's daily driver. Only install, clear, or uninstall the `.dev` package. Never run `adb shell pm clear` or `adb uninstall` against the production or `.preview` package.
3. **Publishing.** `eas update`, `eas build`, `eas submit`, and anything else that reaches the Expo or Play servers is outward-facing. OTA updates land on real devices. Run them only when ril asks, and name the channel before you do.

## Dev loop

- `pnpm install` installs. Worktrees get this from the `t3.json` setup script. While `.t3/setup-running` names a live PID, wait for it. It ends with `.t3/setup-done` or `.t3/setup-failed`.
- `vp` is Vite+, the task runner, test runner, formatter, and linter. It is a dev dependency, so run it as `pnpm vp <command>` unless a global `vp` is on your PATH. Package scripts run with `pnpm vp run <script>`.
- `pnpm vp run mobile:install android` installs the dev client that matches this checkout's native fingerprint on the only connected device or emulator. It reuses a cached APK and builds only when native inputs changed. Prefer it over `expo run:android` or `gradlew`, which rebuild from scratch.
- `pnpm vp run --filter @kindle-drop/mobile dev:client` starts Metro for the dev client.
- `android/` is generated by `expo prebuild` and is gitignored. Native configuration lives in `apps/mobile/app.config.ts` and config plugins, never in `android/`.

## Verifying

- Before you push, run `pnpm vp run check:changed`. It formats, lints, typechecks, and runs the tests affected by your changes.
- While you iterate, run `pnpm vp test run <files>`.
- **Do not run repo-wide checks** (`pnpm vp run test`, `pnpm vp run typecheck`) unless ril asks. CI owns the full suite.
- Test meaningful logic and observable behavior. Do not render components to assert props, and do not add tests that mirror the implementation.
- Logic, data, and state bugs get a failing test first, then the fix. Purely visual bugs get before and after screenshots as proof and no test.
- `it.effect` runs on a `TestClock`. Advance time with `TestClock.adjust`. No sleeps, polling loops, per-test timeouts, retries, or `Date.now()` deltas. Await the `Deferred` or the event that marks the milestone. Lint enforces this.
- `it.skip` needs a tracking issue on the line above: `// quarantine: #12 <why>`.
- Upon request, user-visible changes get one pass on a real device with the `test-kindle-drop-android` skill. Ask before driving a device.

## Where code lives

- `apps/mobile`: the Expo app. `src/components/ui` is the UI kit, `src/features/<feature>` holds screens and feature logic, `src/state` holds atoms, `src/persistence` holds storage services, and `src/lib` holds small shared modules.
- `oxlint-plugin-kd`: this repo's lint rules, ported from T3 Code.
- `oxlint-plugin-anti-slop`: vendored [anti-slop](https://github.com/dmmulroy/anti-slop) rules. Update it with the `install-anti-slop` skill; never overwrite it. Provenance is in its `UPSTREAM.md`.
- `scripts`: repo tooling (`check-changed`, `setup-worktree`, `sync-reference-repos`).
- `.repos/effect-smol`: a read-only Effect source checkout at the installed version, gitignored. Read `.repos/effect-smol/LLMS.md` before writing Effect code and prefer its patterns over invented ones. Never edit or import from it. `pnpm vp run sync:repos` refreshes it.

## Taste

- Inferred types over annotations. `any` is the enemy. Parse external data with `Schema` at the boundary and trust internal types after that.
- Reusable Effect functions use `Effect.fn("Service.operation")` with a stable span name. Keep `Effect.gen` for inline programs and layer construction.
- State lives in Effect atoms (`effect/reactivity` with `@effect/atom-react`). Services are Effect `Context` tags provided by layers. Components read atoms and stay dumb.
- The React Compiler owns memoization. Do not write `useMemo`, `useCallback`, or `React.memo`.
- React effects are for synchronizing with something outside React. Derive in render and act in handlers. `kd/react-effect-budget` holds each file to its count in `scripts/effect-budget.json`. A new effect states its reason with `// oxlint-disable-next-line kd/react-effect-budget -- <why>`.
- `components/ui` exports own their look. Pick a `variant` or `size` rather than restyling one with `className`. Colors come from theme tokens, never literals.
- Default to no comment. Write one only for a constraint, an external quirk, or an invariant the code cannot show, in four lines at most. `kd/no-low-value-comments` enforces the cap.
- No continuously repainting animations. They peg the GPU on high-refresh displays.

## Documentation

- `docs/internals/` is for decisions and their reasons, constraints that span modules, and traps that are hard to discover from the source. If reading the code answers the question, leave it out.
- When a documented decision changes, rewrite or remove the text. Do not append a second account.
- Do not commit plans, research notes, or scratch files.

## Commits and pull requests

- Never open a PR unless ril asks.
- Conventional commit titles in plain language: `fix(mobile): settings no longer flashes on open`. Keep the body short.
- PR body: the problem in a sentence or two, then how you fixed it. Open a real PR, not a draft, rebased onto the latest `main`.
- UI changes need before and after screenshots. Motion needs a short video.
